01 · Architecture

Four services. One observable event pipeline.

The visual model below is intentionally simple: an HTTP request enters the platform, state is persisted, an event is queued, a worker processes it, and telemetry tells operators what happened.

01

API Gateway

Receives REST traffic, validates requests, exposes health endpoints and hands work into the asynchronous workflow.

02

Event Service

Coordinates event creation and delivery with retry-aware processing and idempotency protections.

03

Worker Service

Consumes queued work concurrently, executes business processing and safely retries transient failures.

04

Data + Cache

PostgreSQL provides durable state while Redis supports low-latency data access and coordination.

04 · Engineering story

The recruiter view and the engineer view are both here.

Instead of making the visitor decode infrastructure terminology, the page connects every technical decision to an observable system behavior.

Concurrency

What it means: multiple independent events can be processed at the same time. Why it matters: throughput can grow without turning every request into a sequential bottleneck.

Retries + idempotency

What it means: transient failures can be retried while duplicate delivery does not create duplicate business effects.

Health checks

What it means: the platform continuously exposes service health so orchestration can distinguish healthy capacity from unhealthy instances.

Autoscaling

What it means: Kubernetes can move the worker fleet from a small baseline toward more replicas when workload increases.

Observability

What it means: Prometheus metrics and Grafana dashboards make latency, throughput, failures and recovery visible rather than guessing from logs.

Chaos testing

What it means: controlled failures were used to validate recovery behavior across three failure scenarios.

07 · The story in motion

From one request to a resilient distributed workflow.

Each step has a human-readable explanation and an engineering reason behind it.

01

A request arrives

A user or another service sends a REST request. The API layer validates it and returns quickly instead of waiting for every downstream task.

POST /events → 202 Accepted · event_id=evt_42
02

State becomes durable

The event is recorded in PostgreSQL so the platform has a durable source of truth even if a process or container disappears.

postgres → INSERT event(status="queued")
03

The queue absorbs the spike

AWS SQS separates incoming traffic from background processing. Sudden bursts can wait safely instead of overwhelming workers.

sqs.send(message) → queue_depth=31
04

Workers process concurrently

Multiple worker instances can process independent events in parallel. Kubernetes gives the workload a scalable execution environment.

worker-01 · worker-02 · worker-03 · worker-04
05

Failure becomes a recoverable event

If a worker fails, retry logic and idempotency protect the workflow from losing work or producing duplicate business effects.

attempt=2 → retry → idempotency_key=evt_42 → safe
06

Observability closes the loop

Prometheus metrics and Grafana dashboards expose latency, throughput, health and recovery behavior so the system can be operated rather than guessed at.

latency=137ms · throughput=118/s · healthy=true

09 · Interview mode

Designed to survive the “why did you build it this way?” question.

Architecture decision
“Why not process everything synchronously?”

Because the project demonstrates how a distributed platform handles variable workload and transient failure. A queue creates a boundary between fast request handling and slower background work.

Why SQS? To buffer asynchronous work and decouple producers from consumers.
Why idempotency? Retries are useful only when repeated delivery cannot accidentally repeat the business effect.
Why Kubernetes? To provide health-aware orchestration and horizontal scaling for containerized services.
Why Redis? To keep frequently accessed state/cache operations low-latency without replacing durable PostgreSQL state.
Why Prometheus/Grafana? To turn system behavior into measurable signals: latency, throughput, health and failures.
